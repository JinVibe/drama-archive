# ADR-011 — Guest-first Authentication

- **Status:** Accepted
- **Date:** 2026-09-27
- **Related:** PRD FR-06~FR-08, DATA_MODEL §7, MVP_BACKLOG DM-401~404, Epic 4

## Context

`봤어요` 기록은 이 서비스의 핵심 가치이지만, 기록을 하려면 먼저 회원가입을 해야 한다는 조건은 첫 방문자의 대부분을 이탈시킨다. 반대로 사용자 데이터를 다루는 순간 개인정보보호법·정보통신망법 준수 의무가 생긴다.

두 가지를 동시에 만족해야 한다.

1. 처음 온 사용자가 **아무 절차 없이** 작품을 기록할 수 있어야 한다.
2. 수집하는 개인정보는 **법이 요구하는 최소한**이어야 하고, 처음부터 그 근거가 문서화되어 있어야 한다.

이 서비스는 결제·성인·금융·의료 도메인이 아니므로 본인확인(휴대폰 인증, CI/DI) 의무가 없다. 비밀번호를 직접 관리하면 유출 시 책임과 운영 부담만 커진다.

## Decision

**게스트 우선(Guest-first) + 소셜 로그인 승격(Upgrade)** 모델을 채택한다.

```text
첫 방문
  → 봤어요 클릭
  → 서버가 익명 app_user 생성, 서명된 UUID를 HttpOnly 쿠키로 발급
  → 회원가입 화면 없이 계속 기록
  → 다른 기기 / 공유 카드 / 보관 보장이 필요할 때
  → 소셜 로그인으로 "연결" (같은 app_user에 identity 추가)
```

### 1. 계정 모델

- `app_user`는 익명이든 로그인이든 동일한 행이다. 구분은 `user_identity` 존재 여부.
- `user_identity (user_id, provider, provider_subject)` — provider별 고유 ID만 저장. 이메일·프로필 이미지는 필수 수집 항목이 아니다.
- 익명 사용자는 `anonymous = true`, 승격 시 `false`로 바뀌며 `upgraded_at`을 기록한다.
- 쿠키에는 서버 서명된 user UUID만 담는다. `HttpOnly; Secure; SameSite=Lax`, 만료 1년.

### 2. 로그인 수단

| 순위 | 수단 | 이유 |
|---|---|---|
| 1 | 카카오 | 국내 사용자 마찰 최소. 닉네임만으로 연결 가능 |
| 2 | 네이버, 구글 | 커버리지 |
| 3 | 이메일 magic link | 소셜 계정을 쓰지 않는 사용자용 fallback (Epic 4 이후) |
| — | Apple | iOS 네이티브 앱을 출시할 때만 (App Store 규정). 웹 전용인 동안은 불필요 |
| — | Passkey | 계정 복구 UX가 아직 일반 사용자에게 낯설어 MVP 제외 |

자체 비밀번호 로그인은 만들지 않는다.

### 3. 수집 항목 (최소수집 원칙, 개인정보보호법 §16)

| 단계 | 수집 | 근거 |
|---|---|---|
| 익명 | 쿠키 UUID, 시청 기록, 메모 | 서비스 제공 (계약 이행) |
| 로그인 | + provider 고유 ID, 닉네임 | 계정 연결·다기기 동기화 |
| 선택 | 이메일 | 계정 통지용. 사용자가 거부해도 서비스 이용 가능 |

수집하지 않는 것: 주민등록번호, 전화번호, 생년월일, 성별, 친구 목록, 프로필 이미지 원본. 소셜 로그인 scope는 위 항목만 요청한다.

쿠키 UUID도 온라인 식별자로서 개인정보에 해당하므로 익명 단계부터 개인정보처리방침에 명시한다.

### 4. 동의

- 익명 단계: 별도 동의 화면 없음. 쿠키 사용은 개인정보처리방침에 고지.
- 소셜 연결 시 **필수 동의는 2개만**: 이용약관, 개인정보처리방침.
- 마케팅·푸시·광고성 메일은 별도 **선택** 동의 (정보통신망법 §50).
- 동의 시각과 약관 버전을 `user_consent`에 기록한다.

### 5. 만 14세 미만 (개인정보보호법 §22의2)

나이를 수집하지 않으므로 법정대리인 동의 절차를 만들 수 없다. 따라서:

- 이용약관에 "만 14세 이상만 이용 가능" 명시
- 소셜 연결 시 "만 14세 이상입니다" 체크 1개 (동의 기록에 포함)
- 익명 단계에서는 나이 관련 정보를 일절 묻지 않는다

### 6. 보유기간과 파기

| 대상 | 정책 |
|---|---|
| 익명 사용자 | 마지막 활동 후 **90일** 무활동 시 자동 삭제 (Airflow `anonymous_user_cleanup` DAG) |
| 로그인 사용자 | 탈퇴 즉시 삭제. `app_user` 삭제 시 `user_drama_state`, `memory_note`, `user_identity`, `user_consent` cascade |
| 백업 | 백업 보관 주기(예: 30일) 경과 후 완전 파기. 처리방침에 기한 명시 |
| 관계 법령 보존 의무 | 이 서비스에는 전자상거래법상 거래 기록이 없으므로 해당 없음. 유료 기능 도입 시 재검토 |

### 7. 병합 규칙

익명 사용자가 소셜 연결을 시도했는데 해당 provider 계정이 이미 다른 `app_user`에 연결된 경우:

1. 익명 사용자의 `user_drama_state`, `memory_note`를 기존 계정으로 이동
2. 같은 drama에 대한 상태가 양쪽에 있으면 **더 최근 `updated_at`** 이 이긴다
3. 익명 `app_user`는 `status = 'MERGED'`, `merged_into_id`로 기존 계정을 가리킨다 (drama 테이블과 동일한 패턴)
4. 쿠키는 기존 계정 UUID로 재발급

### 8. UGC (memory_note)

- 기본값 **PRIVATE**. 공개 옵션은 신고·블라인드·관리자 검토 기능이 완성된 뒤 연다 (PRD FR-07).
- private 메모는 검색 corpus, GraphRAG corpus, telemetry 어디에도 들어가지 않는다 (DATA_MODEL §14).

### 9. 경계

- 사용자별 상태(`봤어요`)는 공개 페이지 캐시(ISR/Redis)에 절대 섞이지 않는다. 클라이언트가 별도 API로 가져온다 (ARCHITECTURE §5.3).
- 익명 기록은 브라우저 하나에 묶인다. 이는 한계가 아니라 승격 동기다. UI에 "로그인하면 다른 기기에서도 이어집니다" 한 줄로 안내한다.

## Consequences

**장점**

- 첫 기록까지의 클릭 수: 1
- 비밀번호·이메일 인증·본인확인 인프라 불필요
- 수집 항목이 적어 개인정보 유출 시 피해 범위와 책임이 작다
- 익명 자동 삭제로 저장 비용과 보유기간 리스크가 함께 줄어든다

**단점 / 감수하는 것**

- 익명 사용자는 브라우저 데이터 삭제 시 기록을 잃는다
- 병합 로직이 필요하다 (§7)
- 소셜 provider 장애 시 신규 승격이 막힌다. 기록 자체(익명)는 영향 없음
- 사용자 수 지표에 익명 계정이 섞이므로 분석 시 `anonymous` 필터가 필요하다

## Removal condition

다음 중 하나가 발생하면 이 결정을 재검토한다.

- 유료 기능·결제 도입 → 본인확인 및 거래 기록 보존 의무 발생
- 익명 → 로그인 전환율이 측정 후 목표 대비 현저히 낮아 익명 단계가 무의미해질 때
- iOS 네이티브 앱 출시 → Apple 로그인 추가
